# BANDITBLOX treasury

The Node 22 service owns player accounts, opaque HTTP-only sessions, the PostgreSQL double-entry ledger, crypto games, chat, and the deposit watcher. The public frontend, player API and administrator panel share one origin. The Docker Compose stack exposes Caddy on `PUBLIC_PORT` (default 3000).

For the `durov.me` deployment, the host Caddy site reverse-proxies to `127.0.0.1:3000`. Use `PUBLIC_BIND_ADDRESS=127.0.0.1`, `COOKIE_SECURE=true`, and `ALLOW_ORIGIN=https://durov.me`. `TRUSTED_EDGE_PROXY` is the exact Compose gateway address seen by the inner Caddy; check it if recreating the Docker network. Do not trust arbitrary client forwarding headers or publish the plaintext admin port. The apex A record must point only to this server; remove records for any previous web host. Verify publicly trusted HTTPS before enrolling custody or entering RPC credentials.

## Run and verify

Use `npm ci` inside `treasury/`, then `npm run build`. For the full suite, install Chromium with `npx playwright install chromium` and run `npm test`. Docker is required. The test runner creates and removes an isolated PostgreSQL container, applies migrations twice, and runs the unit, API, ledger, chain and browser suites. To use an installed Chromium binary set `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`.

From the project root, `./deploy.sh` builds the backend, applies recorded migrations and rolls the two replicas. Database data lives in the Compose volume. Supply the database password, vault master key and bootstrap admin credentials through the deployment environment. Use the domain's HTTPS listener and secure cookies for real funds. Preserve the vault key and wallet backups separately from the database.

## Deposit setup

**Permanent direct addresses are the only active deposit flow after migration 019.** The launch scope is seven routes across four networks. An address appears only after its worker and scanner are ready; deployment alone does not activate deposits. Previously issued direct addresses continue to be monitored under their existing chain and asset controls. Hosted payment records are archived and no longer reconciled automatically.

| Network | New deposit routes | Collection destination | RPC secret |
| --- | --- | --- | --- |
| Ethereum mainnet, ID 1 | ETH and USDT ERC-20 | Owner-controlled public EVM address | `rpc:ETH` |
| BNB Smart Chain mainnet, ID 56 | BNB and USDT BEP-20 | Owner-controlled public EVM address | `rpc:BSC` |
| Polygon PoS mainnet, ID 137 | POL and USDT on Polygon | Owner-controlled public EVM address | `rpc:POL` |
| Solana mainnet-beta | Native SOL only | Separate public Solana owner address | `rpc:SOL` |

The same EVM collection address may be used on all three EVM networks, but each must be configured and verified separately. A Solana collection address is a different address. Collection destinations cannot be player receive addresses, the fee sponsor or token contracts. The admin API pins each saved destination; there is no address replacement or seed reset button.

### Public RPC preparation

The following public, keyless endpoints passed read-only mainnet probes on November 26, 2026. They are configuration candidates, not built-in runtime defaults or an availability guarantee. Each endpoint must be saved as its encrypted `rpc:<CHAIN>` setting; the services do not read an RPC URL from an environment-variable fallback.

| Setting | Public endpoint |
| --- | --- |
| `rpc:ETH` | `https://ethereum-rpc.publicnode.com` |
| `rpc:BSC` | `https://bsc-rpc.publicnode.com` |
| `rpc:POL` | `https://polygon.drpc.org` |
| `rpc:SOL` | `https://api.mainnet.solana.com` |

The EVM probes checked chain identity, full transactions, canonical block-hash account and token reads, token decimals, block-hash-filtered transfer logs, and matching receipts. Polygon's PublicNode endpoint rejected the required log method with HTTP 403, so a successful chain-ID request alone would have selected an unusable provider. Expanded Solana probes on November 27, 2026 checked mainnet genesis, a fresh finalized head, both retention methods, address signature history, parsed and base64 version-1 transaction reads, canonical signature-only block inclusion and finalized historical signature status. The official endpoint returned a 2,439-byte version-1 transaction; its signature-only block response fit the scanner's 4 MiB limit. Its zero first-available-block result differed from its recent minimum ledger slot, so neither a saved URL nor that zero establishes archival coverage. Read probes do not establish successful broadcasting or prove that historical evidence remains available after a long outage.

Free RPC access does not pay network fees or provide a service-level agreement. The [Solana public endpoint documentation](https://solana.com/docs/references/clusters) describes shared IP, per-method and bandwidth limits, subject to change, and HTTP 429 backoff. [dRPC's Polygon connection details](https://drpc.org/chainlist/polygon) publish its public endpoint. Check current provider terms and limits again before opening deposits, keep issuance paused during preparation, and use the scanner's actual readiness rather than treating a saved URL as activation. Never reset a permanent address, move its cursor past missing history, or mark an ambiguous signed sweep complete to work around a public endpoint's limits.

### Activate direct deposits

1. Deploy the migrations, both API replicas and the separate `custody_worker` service using `./deploy.sh`. Open `/admin` over verified HTTPS and enable an authenticator under **Security**. Pause new deposits in **Settings** during setup.
2. Open **Direct wallets**. The isolated worker publishes its RSA-3072 wrapping-key fingerprint. Verify it against the deployment. The private file exists only in the `custody_keys` volume at `/var/lib/empireblox-custody/private/worker-rsa.pk8`; the API containers do not mount this volume. Preserve its ownership, directory mode `0700` and file mode `0400` or `0600` when backing it up or restoring it.
3. Generate a dedicated cryptographically random **32-byte seed offline**, keep its 64-character hexadecimal backup offline, and verify the backup before enrollment. Enter that seed once in **Signing worker**, confirm the backup checkbox, and supply a fresh authenticator code. This is raw seed material, not a seed phrase or an existing wallet private key. Do not reuse `TREASURY_MASTER_KEY`. Browser WebCrypto encrypts the decoded bytes to the worker's public key with RSA-OAEP/SHA-256 and the key ID as the OAEP label; the API stores only the envelope. The input is cleared, and the seed cannot be read or replaced through the panel.
4. Refresh until **Signing key: Ready**. Expand each network, open **Edit network settings**, and save its HTTPS mainnet RPC and public collection destination with a fresh authenticator code. RPC credentials are encrypted in the vault and remain write-only. These four RPCs must be changed through **Direct wallets** after enrollment. Saving an RPC enables that chain and invalidates its old readiness checkpoint; check the accepted assets and exact minimums under **Assets**.
5. Wait for each required scanner to report **Current** and address issuance to report **Ready**. EVM providers must serve full blocks, transaction receipts, block-hash-filtered logs, EIP-1898 balance/code/token reads, gas estimates and raw transaction submission. Solana requires complete finalized address-signature history, parsed and base64 transaction reads supporting version 1, signature-only canonical blocks, historical signature status, retention metadata, account/rent/fee queries and transaction submission. A checkpoint must have committed and remain current within two minutes. Incorrect network identity or incomplete evidence fails closed.
6. For USDT collection, fund the public **Gas sponsorship** address with **ETH on Ethereum, BNB on BNB Smart Chain and POL on Polygon**. These are three separate network balances. Do not send USDT or SOL to pay these fees. This is a dedicated worker-managed address, distinct from the collection address. Native sweeps pay fees from the deposit; native SOL also respects account rent requirements.
7. Check the full saved collection destination in the receiving wallet. On each network, check its verification box and choose **Enable sweeps** using a new authenticator code. A successful custody change consumes that 30-second code; wait for the next code for another change. Mutations are also rate limited across replicas. Sweep controls and address issuance are independent.
8. With public access restricted, briefly resume address requests under **Settings** to obtain controlled test-account addresses, then pause requests again. Verify a small above-minimum transfer on each intended route through **Admin → Deposits** to `credited`, then through **Recent sweep jobs** to `Completed`, and finally at the collection wallet. Only then resume requests and open verified routes to players. Local fixture tests do not establish a live RPC connection or a successful mainnet transfer.

Players open **Wallet** in the header. Its overview, deposit currency/network selectors, permanent address, local QR, copy action and withdrawal review use the same popup. There is no deposit amount input or checkout redirect. Send an amount at or above the displayed route minimum; the server credits the actual received amount after verifying the canonical transfer, required confirmations and review hold. A QR code, screenshot or pending observation is not a credit. Native ETH/BNB/POL/SOL and USDT on Ethereum/BNB Chain/Polygon are the only new direct choices. Playing-currency selection remains separate from deposit-currency selection, and deposit readiness does not hide existing currency balances.

### Addresses, recovery and sweeping

Registration assigns available managed addresses without contacting an RPC. A temporarily unavailable worker, busy scanner or empty Solana pool does not prevent signup; existing accounts backfill when they request a ready network. Each user has one EVM receive path reused across Ethereum, BNB Chain and Polygon and a separate Solana path. Once assigned, a user's address and owner cannot be changed. The worker deterministically refills its pool to 32 unassigned Solana public addresses each cycle.

Migration 020 adds durable Solana address-history progress without changing ownership or financial records. The scanner pages assigned native addresses and existing legacy token accounts, pins each coverage target, and retains completed pages across later failures or restarts. It compares both available-history floors, verifies canonical inclusion and requires a fresh finalized head. Missing or discontinuous history suspends issuance; an existing populated wallet with a zero cursor requires reconciliation. Do not delete progress or reset a cursor to bypass those checks. Scanner and sweeper share bounded per-origin transport pacing, response limits and retry cooldowns within each process; additional replicas or other clients sharing the IP reduce the available public-RPC headroom.

The seed is used directly as the BIP32/SLIP-0010 master seed. EVM receives derive at `m/44'/60'/0'/0/index`; the dedicated EVM fee sponsor is `m/44'/60'/0'/1/0`. Solana derives with ed25519 SLIP-0010 at `m/44'/501'/index'/0'`. The worker/offline helper `restoreCustodyPublic(seed, index)` in `src/custody/keys.ts` verifies these public addresses without a database, vault key, RPC or wrapping file. Back up the seed, wrapping-key volume, vault key and database separately. The database contains the permanent user/index assignments and exact signed-job history. Losing the wrapping volume stops readiness instead of generating replacement identities; restore the original volume. The offline seed can reconstruct keys, but does not reconstruct ownership or broadcast history.

Only canonically verified deposits already credited by a balanced deposit journal to a managed address can enter the sweep queue. The queue commits exact signed bytes and transaction IDs before broadcast and reuses those bytes after a crash or lost acknowledgement. It never posts another player credit. Gas sponsorship is excluded from deposit credit, and internal transactions cannot be reused as deposit or withdrawal proof. Native sweeps collect the deposit less fees; token sweeps use one bounded sponsor transaction and then the exact credited token amount. The player keeps the original confirmed deposit credit; collection fees do not create another player debit. Hard fee caps, aggregate sponsor budgets, per-source sequencing and chain checks apply.

Use **Direct wallets → Pause sweeps** to stop new signatures and broadcasts on a network. Already submitted transactions still need receipt reconciliation. A job in `Needs review` fences further jobs from that source; do not manually resend or delete its transaction history. Expired blockhashes, unknown nonces, reorganizations, failed or ambiguous receipts require reconciliation before any operator action. **Settings → Pause deposits** blocks registration-time address allocation and address requests, including redisplay through the deposit endpoint. It does not revoke permanent addresses, cancel submitted transactions or stop detection and credit to previously issued addresses. Keep their network RPCs and chain/asset monitoring enabled; disabling a chain or asset is a separate monitoring control.

Legacy xpub and imported Solana assignments keep their original owners and remain monitored with their original network RPCs. They are not swept by the managed signer; retain their original offline keys and collect them manually. BTC, TRON and Solana USDT are outside new direct issuance. Historical balances, transactions and withdrawals remain available under their existing controls.

### Retired checkout records

Migration 019 removes the old deposit-method setting and merchant secret, clears scheduled invoice checks, and makes historical checkout invoices and transfer claims read-only. The application has no hosted checkout routes, callback handler or background invoice worker. Its public-origin checkout environment variable is no longer used. Do not offer old payment links or expect outstanding hosted payments to reconcile after this cutover; reconcile any outstanding external payment manually against retained evidence before retiring the old deployment, without duplicating an existing ledger credit.

Historical migrations 013, 015 and 017 remain unchanged. Their invoices, tracking references, transfer claims, settled journals and audit entries remain available as archived evidence in deposit and account history. Archived checkout rows do not enter the active pending-deposit count. Direct-address scanners and custody transaction fencing continue to protect previously issued addresses and signed transactions.

## Wallet and games

Currency choice, deposit addresses, balances, game snapshots and history live in PostgreSQL. The site uses session cookies. Native Mines and Blackjack stakes are decimal strings converted to integer minor units. Cases, Upgrader, rewards and battle entries use the existing catalog of 600 units per USD, converted with short-lived market quotes. The server checks the quote on entry. Each battle keeps its entry price through settlement or refund. Market service failure suspends new priced entries until a fresh quote is available.

After all serving replicas have upgraded, set an inclusive minimum and maximum in **Admin → Settings → Wager limits**. A zero minimum or blank maximum disables that bound. Limits are in USDT across all paid games, not in the playing coin. Stakes use recent market conversion at acceptance; pricing failures cannot silently admit unpriced exposure. Paid additions count toward the hand maximum, and refunds, payouts and free entries are not new bets. The separate USD-based reward schedule and native currency histories remain intact.

`GET /api/games/bet-limits` and authenticated `GET /api/admin/bet-limits` return `{"min_usdt":"0","max_usdt":null}` on a new installation. An administrator can `PUT /api/admin/bet-limits` with both fields to replace the pair atomically. Supply nonnegative decimal strings with at most 18 fractional and 60 integer digits. A non-null maximum must be positive and at least the minimum.

The minimum applies to each actual player debit. The maximum applies to the total cash put at risk by that player in that round: blackjack insurance, splits and doubles add to the previously booked stakes at their individual entry rates. A battle uses the cost of that player's seat **after** borrowing, not the sticker price or the combined pot. Late seats keep the original asset entry cost but must pass current limits at a fresh market rate. Rejecting an optional action does not change the hand or balance. Hits, stands, declining insurance, reveals, cashouts, refunds, prizes, bots, free claims and successful request replays do not place a wager or recheck the limits.

Each real debit records its asset minor units and server-issued quote. BNB, BTC, ETH, POL, SOL and USDT use a single Coinbase USD exchange-rate response. TRX uses the bid/ask midpoints for TRX/USD and USDT/USD from **one public Kraken ticker response**. Both books must be present, positive and non-crossed. The two reciprocals share one rounding factor: the stored USD legs must be accurate to one part in 10^16, and their TRX/USDT ratio stays exact. There is no dollar-peg assumption, rounded catalog-unit conversion, or cross-provider fallback for a missing leg.

Quotes expire within two minutes of observation (including HTTP cache age), checked against the database wall clock at acceptance. New paid stakes need a verified valuation even with unbounded limits. A legacy native blackjack hand lacking an opening USDT valuation can finish without adding funds, but cannot add risk under a finite maximum.


## USDT, withdrawals and account activity

Players choose USDT once. New direct transfers on Ethereum, BNB Chain and Polygon credit the same USDT ledger balance; previously assigned Solana USDT transfers remain monitored. The ledger uses 18 decimals and converts each transfer from its network precision. The deposit history keeps the original chain and transaction ID. A disabled or unready network is labelled unavailable in the deposit form. Other supported cryptocurrencies retain their own balances.

The account icon opens `/account/profile`. Profile, Statistics, Transactions, Bet history, Rewards, Notifications and Security are the seven account sections, each with a shareable route. The profile's **Open wallet** action opens the same financial popup as the header; legacy deposit and withdrawal routes also open that popup. Authentication scopes every player record. The header bell shows the five latest notifications without leaving the current page. The profile overview shows the selected balance, reward progress and recent deposits. Players can update their username and password in Security. Balance and in-game payout displays normally round USDT to three decimals, ETH to five, POL to two and BNB to four; a nonzero amount that would otherwise display as zero keeps its exact value. Battle results retain their entry currency and expose exact payouts in their detail text. The ledger, game stakes, receipts and withdrawal confirmations retain the underlying precision. Statistics show cumulative net results or daily wagered amounts by UTC date placed for the selected currency over 7, 30 or 90 days. Settled paid wagers count toward statistics. Individual results include stakes, payouts and game-specific details. Active rounds hide unrevealed outcomes.

Withdrawal requests reserve the exact amount immediately. Players may cancel before review. Under **Admin → Withdrawals**, claim the request and verify the destination, network and amount against the custody wallet. The assigned reviewer approves the request before signing and broadcasting it externally. The reviewer can return reserved funds before sending or record the broadcast transaction ID after sending. Record the on-chain transaction ID once per request. The API records the operator's attestation; the isolated signing worker only collects eligible deposits and does not sign player payouts or automatically confirm withdrawals.

## Player management and notifications

Under **Admin → Users**, search by full or partial email, username or account ID. Use the status filter to find active, suspended or banned accounts. Select a row for balances, deposit addresses, statistics, deposits, withdrawals, bet results, transactions and operator actions. Under **Controls**, enter a reason and review each adjustment, suspension, ban or restoration. Adjustments post a balanced journal. Bans and suspensions revoke player sessions immediately. A temporary suspension expires at the chosen time.

For a pending deposit, **Deposits → Hold credit for review** preserves the observation and blocks credit. Release the hold to let the watcher recheck the canonical block and confirmation count. Players receive a notification when the scanner detects a deposit and again when it credits the balance. EVM detection follows the configured reorganization safety lag. Outbound requests notify the player when requested, claimed for review, approved, returned or recorded as sent. The withdrawal receipt includes the operator's transaction hash.

Notifications persist in PostgreSQL. A long poll wakes after an event commits, including events written by another replica. Reopening the inbox loads saved activity and read state.

## Level rewards

The Rewards section shows lifetime settled wager, current level, next threshold and available bonuses. Each of the nine tiers contains five levels. Players can claim each earned level once. A claim posts the listed bonus to the unified USDT ledger and records a receipt. Unclaimed levels remain available after reaching higher ones. The Rewards section displays the wager-level program. Previously settled daily-pack entries remain in account history.

New stakes retain their entry-time valuations. Older rounds use their historical valuation where available, not today's market price. The reward screen discloses excluded unpriced historical wagers. Free entries, cancelled battles, deposits, operator credits and bonuses contribute zero wager.

VIP thresholds remain in USD. New settled wagers use the actual USD value of every debit (including USDT); player/admin progress also returns `wagered_usdt`. Statistics keep native stakes and payouts with a separate daily `wagered_usdt`. Reporting truncates each valuation to 18 fractional places, never before a limit comparison. Legacy USD progress stays under its original rules. Legacy USDT is known by denomination; old native wagers with no recorded USDT leg are disclosed via `unpriced_usdt`. The old `users.wagered` sum of mixed minor units is not used for admissions or reporting.

Both player and admin transaction histories can filter deposits, withdrawals, bets, rewards and balance adjustments. A bet filter includes stakes, game payouts and returned battle entries. A withdrawal reservation or refund appears with the current request status and any recorded hash.
