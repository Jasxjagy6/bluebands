# BANDITBLOX treasury

The Node 22 service owns player accounts, opaque HTTP-only sessions, the PostgreSQL double-entry ledger, coin games, chat, and the deposit watcher. The public frontend, player API and administrator panel share one origin. The Docker Compose stack exposes Caddy on `PUBLIC_PORT` (default 3000).

For the `durov.me` deployment, the host Caddy site reverse-proxies to `127.0.0.1:3000`. Use `PUBLIC_BIND_ADDRESS=127.0.0.1`, `COOKIE_SECURE=true`, and `ALLOW_ORIGIN=https://durov.me`. `TRUSTED_EDGE_PROXY` is the exact Compose gateway address seen by the inner Caddy; check it if recreating the Docker network. Do not trust arbitrary client forwarding headers or publish the plaintext admin port. The apex A record must point only to this server; remove records for any previous web host. Verify publicly trusted HTTPS before enrolling custody or entering RPC credentials.

## Run and verify

Use `npm ci` inside `treasury/`, then `npm run build`. For the full suite, install Chromium with `npx playwright install chromium` and run `npm test`. Docker is required. The test runner creates and removes an isolated PostgreSQL container, applies migrations twice, and runs the unit, API, ledger, chain and browser suites. To use an installed Chromium binary set `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`.

From the project root, `./deploy.sh` builds the backend, applies recorded migrations and rolls the two replicas. Database data lives in the Compose volume. Supply the database password, vault master key and bootstrap admin credentials through the deployment environment. Use the domain's HTTPS listener and secure cookies for real funds. Preserve the vault key and wallet backups separately from the database.

## Deposit setup

**Permanent direct addresses are the only active deposit flow after migration 019.** The launch scope is seven routes across four networks. An address appears only after its worker and scanner are ready; deployment alone does not activate deposits. Previously issued direct addresses continue to be monitored under their existing chain and asset controls. Hosted payment records are archived and no longer reconciled automatically.

| Network | New deposit routes | Collection destination | RPC configuration |
| --- | --- | --- | --- |
| Ethereum mainnet, ID 1 | ETH and USDT ERC-20 | Owner-controlled public EVM address | dRPC primary; Alchemy fallback |
| BNB Smart Chain mainnet, ID 56 | BNB and USDT BEP-20 | Owner-controlled public EVM address | dRPC primary; Alchemy fallback |
| Polygon PoS mainnet, ID 137 | POL and USDT on Polygon | Owner-controlled public EVM address | dRPC primary; Alchemy fallback |
| Solana mainnet-beta | Native SOL only | Separate public Solana owner address | Alchemy directly |

The same EVM collection address may be used on all three EVM networks, but each must be configured and verified separately. A Solana collection address is a different address. Collection destinations cannot be player receive addresses, the fee sponsor or token contracts. The admin API pins each saved destination; there is no address replacement or seed reset button.

### RPC provider configuration

The operator panel accepts one dRPC API key and constructs the HTTPS JSON-RPC endpoints for Ethereum (`ethereum`), BNB Smart Chain (`bsc`) and Polygon (`polygon`) at `https://lb.drpc.live/{network}/{key}`. The key is stored encrypted as `drpc:API_KEY`, never returned by the API, and never sent to player pages. Ethereum, BNB Smart Chain and Polygon use dRPC first. Solana uses Alchemy directly for both scanning and sweeps; the current dRPC free plan excludes Solana.

Configure the dRPC key under **Direct wallets → Network routing**. Add up to ten Alchemy keys for Solana and EVM fallback there; each key is independently encrypted, masked, and removable by slot. When dRPC reports a plan restriction, authentication, rate-limit, server, or transport failure, only that EVM network switches to the Alchemy pool. It automatically retries dRPC after the cooldown (15 seconds initially for throttling, doubling on repeated failures up to 15 minutes; 30 seconds for transport/server errors, five minutes for credentials, and 30 minutes for unsupported plans or methods). Healthy EVM routes remain on dRPC. After throttling, a scanner finishes catch-up on the available fallback before returning to dRPC, rather than losing partial batches to repeated primary retries.

All replicas and the signer share a database-coordinated dRPC budget of four requests/second with a one-request burst, to reduce free-plan throttling. EVM scanners verify the endpoint chain ID once per scan rather than before each individual block read. With the operator's 210M-CU allowance and dRPC's documented 20 CU per standard request, four sustained requests/second is at most about 207.36M CU over 30 days for this deployment's managed clients; other applications using the account consume additional allowance. The [dRPC rate-limit guide](https://drpc.org/docs/howitworks/ratelimiting) also notes network-specific free-tier limits, so actual 429 responses trigger backoff even below an account's advertised burst RPS. Failover pauses new address issuance until the scanners have current checkpoints. Alchemy failures rotate the shared key pool; cooldowns remain in PostgreSQL across replica restarts.

Alchemy traffic shares one conservative database-coordinated budget across scanners, sweep workers and all keys: 120 estimated CU/s plus a 60-CU burst. The local Alchemy [throughput documentation](../docs/content/api-reference/pricing-resources/resources/throughput.mdx) documents an account-wide allowance; additional keys do not increase it.

EVM token-log scans query up to ten blocks per request, filter only assigned recipient addresses in groups of 100, and check every returned log against the saved canonical block hashes; current scanners poll every five seconds for BNB Chain, 15 seconds for Ethereum/Polygon and 30 seconds for Solana. PostgreSQL coordinates one schedule per network across both API replicas, so a second replica does not double normal polling. Solana checks up to four empty addresses against the same finalized snapshot, while nonempty signature pages retain their existing commit boundaries. Scanners with committed catch-up work retry after one second instead of adding the normal polling delay. Routing changes are recorded after releasing scanner locks so a concurrent address request cannot deadlock failover. These limits can delay catch-up and confirmation during a long dRPC outage, but failed scans retain their cursor and retry rather than skipping history. A key switch preserves assigned addresses, ownership, scan cursors and deposit history. The scanner continues monitoring already issued addresses and crediting confirmed transfers while new address issuance is paused. Add, replace or remove provider credentials only while all four network sweeps are paused. Existing installations can continue using stored per-network RPC secrets if no provider key is configured. BTC and TRON monitoring continue using their own node endpoints.

The dRPC key must support the three EVM mainnets and their standard JSON-RPC reads and transaction broadcasts. The Alchemy key must support Solana, plus any EVM networks that need fallback. A saved key only marks configuration: it does not prove that the endpoint is reachable, has the required history, or can broadcast. Wait for each monitor's actual scanner readiness before relying on new address issuance. A populated receive-address set with no saved scan cursor fails closed and requires history reconciliation; the scanner will not fast-forward it to the current tip. Never reset a permanent address, move its cursor past missing history, or mark an ambiguous signed sweep complete to work around unavailable history or provider limits.

### Activate direct deposits

1. Deploy the migrations, both API replicas and the separate `custody_worker` service using `./deploy.sh`. Open `/admin` over verified HTTPS and enable an authenticator under **Security**. Pause new deposits in **Settings** during setup.
2. Open **Direct wallets**, save the dRPC key and add one or more Alchemy keys with fresh authenticator codes. The routing change invalidates scanner freshness; wait for all enabled monitors to establish current checkpoints before treating address issuance as ready. The isolated worker publishes its RSA-3072 wrapping-key fingerprint. Verify it against the deployment. The private file exists only in the `custody_keys` volume at `/var/lib/empireblox-custody/private/worker-rsa.pk8`; the API containers do not mount this volume. Preserve its ownership, directory mode `0700` and file mode `0400` or `0600` when backing it up or restoring it.
3. Generate a dedicated cryptographically random **32-byte seed offline**, keep its 64-character hexadecimal backup offline, and verify the backup before enrollment. Enter that seed once in **Signing worker**, confirm the backup checkbox, and supply a fresh authenticator code. This is raw seed material, not a seed phrase or an existing wallet private key. Do not reuse `TREASURY_MASTER_KEY`. Browser WebCrypto encrypts the decoded bytes to the worker's public key with RSA-OAEP/SHA-256 and the key ID as the OAEP label; the API stores only the envelope. The input is cleared, and the seed cannot be read or replaced through the panel.
4. Refresh until **Signing key: Ready**. Expand each network, open **Edit network settings**, and save the public collection destination with a fresh authenticator code. RPC credentials remain write-only in the encrypted vault; the network editor cannot replace a per-network endpoint. Check the accepted assets and exact minimums under **Assets**.
5. Wait for each required scanner to report **Current** and address issuance to report **Ready**. EVM endpoints must serve full blocks, transaction receipts, range-filtered logs with canonical block hashes, EIP-1898 balance/code/token reads, gas estimates and raw transaction submission. Solana requires complete finalized address-signature history, parsed and base64 transaction reads supporting version 1, signature-only canonical blocks, historical signature status, retention metadata, account/rent/fee queries and transaction submission. A checkpoint must have committed and remain current within two minutes. Incorrect network identity or incomplete evidence fails closed.
6. For USDT collection, fund the public **Gas sponsorship** address with **ETH on Ethereum, BNB on BNB Smart Chain and POL on Polygon**. These are three separate network balances. Do not send USDT or SOL to pay these fees. This is a dedicated worker-managed address, distinct from the collection address. Native sweeps pay fees from the deposit; native SOL also respects account rent requirements.
7. Check the full saved collection destination in the receiving wallet. On each network, check its verification box and choose **Enable sweeps** using a new authenticator code. A successful custody change consumes that 30-second code; wait for the next code for another change. Mutations are also rate limited across replicas. Sweep controls and address issuance are independent.
8. With public access restricted, briefly resume address requests under **Settings** to obtain controlled test-account addresses, then pause requests again. Verify a small above-minimum transfer on each intended route through **Admin → Deposits** to `credited`, then through **Recent sweep jobs** to `Completed`, and finally at the collection wallet. Only then resume requests and open verified routes to players. Local fixture tests do not establish a live RPC connection or a successful mainnet transfer.

The configured deposit threshold is five confirmations on every network and asset, including pending uncredited deposits at the policy migration. Canonical inclusion, review holds and Solana finalized evidence remain required; five EVM blocks do not imply protocol finality.

Players open **Wallet** in the header. Its overview, deposit currency/network selectors, permanent address, local QR, copy action and withdrawal review use the same popup. There is no deposit amount input or checkout redirect. Send an amount at or above the displayed route minimum; the server credits the actual received amount after verifying the canonical transfer, required confirmations and review hold. A QR code, screenshot or pending observation is not a credit. Native ETH/BNB/POL/SOL and USDT on Ethereum/BNB Chain/Polygon are the only new direct choices. New games always use coins. Deposit currency/network selectors remain independent, and deposit readiness never hides existing balances. Convert in Account → Conversion before playing, or convert coins back to crypto before withdrawing.

### Addresses, recovery and sweeping

Registration assigns available managed addresses without contacting an RPC. A temporarily unavailable worker, busy scanner or empty Solana pool does not prevent signup; existing accounts backfill when they request a ready network. Each user has one EVM receive path reused across Ethereum, BNB Chain and Polygon and a separate Solana path. Once assigned, a user's address and owner cannot be changed. The worker deterministically refills its pool to 32 unassigned Solana public addresses each cycle.

Migration 020 adds durable Solana address-history progress without changing ownership or financial records. The scanner pages assigned native addresses and existing legacy token accounts, pins each coverage target, and retains completed pages across later failures or restarts. It compares both available-history floors, verifies canonical inclusion and requires a fresh finalized head. Its capability probe uses a real fee payer from a canonical finalized transaction rather than the System Program address, which providers commonly exclude from address-history indexes. Missing or discontinuous history suspends issuance; an existing populated wallet with a zero cursor requires reconciliation. Do not delete progress or reset a cursor to bypass those checks. Scanner and sweeper share bounded per-origin transport pacing, response limits and retry cooldowns within each process; additional replicas or other clients sharing the IP reduce the available public-RPC headroom.

The seed is used directly as the BIP32/SLIP-0010 master seed. EVM receives derive at `m/44'/60'/0'/0/index`; the dedicated EVM fee sponsor is `m/44'/60'/0'/1/0`. Solana derives with ed25519 SLIP-0010 at `m/44'/501'/index'/0'`. The worker/offline helper `restoreCustodyPublic(seed, index)` in `src/custody/keys.ts` verifies these public addresses without a database, vault key, RPC or wrapping file. Back up the seed, wrapping-key volume, vault key and database separately. The database contains the permanent user/index assignments and exact signed-job history. Losing the wrapping volume stops readiness instead of generating replacement identities; restore the original volume. The offline seed can reconstruct keys, but does not reconstruct ownership or broadcast history.

Only canonically verified deposits already credited by a balanced deposit journal to a managed address can enter the sweep queue. The queue commits exact signed bytes and transaction IDs before broadcast and reuses those bytes after a crash or lost acknowledgement. It never posts another player credit. Gas sponsorship is excluded from deposit credit, and internal transactions cannot be reused as deposit or withdrawal proof. Native sweeps collect the deposit less fees; token sweeps use one bounded sponsor transaction and then the exact credited token amount. The player keeps the original confirmed deposit credit; collection fees do not create another player debit. Hard fee caps, aggregate sponsor budgets, per-source sequencing and chain checks apply.

Use **Direct wallets → Pause sweeps** to stop new signatures and broadcasts on a network. Already submitted transactions still need receipt reconciliation. A job in `Needs review` fences further jobs from that source; do not manually resend or delete its transaction history. Expired blockhashes, unknown nonces, reorganizations, failed or ambiguous receipts require reconciliation before any operator action. **Settings → Pause deposits** blocks registration-time address allocation and address requests, including redisplay through the deposit endpoint. It does not revoke permanent addresses, cancel submitted transactions or stop detection and credit to previously issued addresses. Keep their network RPCs and chain/asset monitoring enabled; disabling a chain or asset is a separate monitoring control.

Legacy xpub and imported Solana assignments keep their original owners and remain monitored with their original network RPCs. They are not swept by the managed signer; retain their original offline keys and collect them manually. BTC, TRON and Solana USDT are outside new direct issuance. Historical balances, transactions and withdrawals remain available under their existing controls.

### Retired checkout records

Migration 019 removes the old deposit-method setting and merchant secret, clears scheduled invoice checks, and makes historical checkout invoices and transfer claims read-only. The application has no hosted checkout routes, callback handler or background invoice worker. Its public-origin checkout environment variable is no longer used. Do not offer old payment links or expect outstanding hosted payments to reconcile after this cutover; reconcile any outstanding external payment manually against retained evidence before retiring the old deployment, without duplicating an existing ledger credit.

Historical migrations 013, 015 and 017 remain unchanged. Their invoices, tracking references, transfer claims, settled journals and audit entries remain available as archived evidence in deposit and account history. Archived checkout rows do not enter the active pending-deposit count. Direct-address scanners and custody transaction fencing continue to protect previously issued addresses and signed transactions.

## Player interface

The shared interface in `assets/interface.css` supplies the lobby, game surfaces, wallet, account pages and receipt alerts. The game catalog supports search combined with Solo/Multiplayer filters. Motion acknowledges navigation, dialog entry and new receipts; reduced-motion settings suppress these effects without bypassing game-result timing.

**Notifications → Sound on/off** controls both browser-generated account chimes and gameplay effects. The preference is saved on this browser and synchronized across its tabs. Browsers require a user interaction before audio can play. Initial unread history stays silent; only new receipt revisions can announce an alert. Marking receipts read does not replay them. Receipt alerts can be dismissed, open the inbox, and pause dismissal while hovered or focused. Financial receipts and read state remain server-owned.

## Wallet and games

All new Mines, Blackjack, Cases, Upgrader and battle stakes/payouts use **COINS**, a separate PostgreSQL ledger asset with 18 decimal places. A catalog unit is exactly one coin. Crypto deposits still credit their original crypto balance (network USDT routes consolidate into USDT). No automatic crypto-to-coin conversion happens on deposit, and no existing balance or purchased round is redenominated.

**Account → Conversion** exchanges **6,000 coins ↔ 10 USDT**, with no conversion fee. Other cryptocurrencies use live server-validated crypto/USDT cross rates from a single provider snapshot. Quotes last at most 30 seconds and cannot outlive their underlying market observation. The receive amount rounds down to the destination’s smallest unit. Both debit and credit commit in one double-entry journal with an immutable receipt. A quote is usable once, request keys are bound to their original quote, and retrying a completed request returns its original receipt even after the quote expires. See [COINS.md](COINS.md).

Coin games use a fixed server quote; a market-provider outage does not disable them or fixed-rate USDT conversions. Native crypto conversion fails closed when its price is missing, invalid or stale. Coinbase supplies supported native/USD and USDT/USD legs in one response; TRX uses both TRX/USD and USDT/USD bid/ask midpoints from one Kraken response. HTTP observation age is included in the two-minute market bound. No client amount, price or local storage value can credit a balance.

**Admin → Settings → Wager limits** retains its existing USDT-equivalent storage/API for operator compatibility: one USDT of limit equals 600 coins. A zero minimum or blank maximum disables that bound. The player-facing rejection states the amount in coins. Every actual debit has a fixed valuation, and Blackjack insurance, splits and doubles count toward the player’s cumulative per-round maximum. Optional-action rejection leaves the hand and balance unchanged. Payouts, refunds, free packs, bots and successful replays are not new wagers.

A previously purchased crypto round can finish, cash out, pay or refund in its original denomination. It cannot accept new crypto exposure: legacy Blackjack must hit/stand or decline insurance instead of adding a crypto stake; owned legacy battles can still be viewed, filled with bots or cancelled. A database trigger also fences crypto stakes from an old API replica during rollout.


## USDT, withdrawals and account activity

USDT deposits have an inclusive minimum of **0.1 USDT per transfer**: 100,000 minor units on Ethereum, Polygon and legacy six-decimal routes, and 100,000,000,000,000,000 units on BNB Chain. The wallet displays the saved route minimum. Managed USDT sweeps use the same 0.1 USDT floor and retain the existing fee and sponsorship caps. Native-coin routes retain their configured native minimums.

Players choose USDT once. New direct transfers on Ethereum, BNB Chain and Polygon credit the same USDT ledger balance; previously assigned Solana USDT transfers remain monitored. The ledger uses 18 decimals and converts each transfer from its network precision. The deposit history keeps the original chain and transaction ID. A disabled or unready network is labelled unavailable in the deposit form. Other supported cryptocurrencies retain their own balances.

The account icon opens `/account/profile`. Profile, Conversion, Statistics, Transactions, Bet history, Rewards, Notifications and Security are the eight account sections, each with a shareable route. The profile's **Open wallet** action opens the same financial popup as the header; legacy deposit and withdrawal routes also open that popup. Authentication scopes every player record. The header bell shows the five latest notifications without leaving the current page. The profile overview shows the coin balance, separate crypto wallet balances, daily-pack progress and recent deposits. Players can update their username and password in Security. Coin balances and game payouts display up to three decimal places. Crypto wallet displays round USDT to three decimals, ETH to five, POL to two and BNB to four; a nonzero amount that would otherwise display as zero keeps its exact value. Battle results retain their entry currency and expose exact payouts in their detail text. The ledger, game stakes, receipts and withdrawal confirmations retain the underlying precision. Statistics show cumulative net results or daily wagered amounts in coins by UTC date placed over 7, 30 or 90 days. Settled paid wagers count toward statistics. Individual results include stakes, payouts and game-specific details. Active rounds hide unrevealed outcomes.

Withdrawal requests reserve the exact amount immediately. Players may cancel before review. Under **Admin → Withdrawals**, claim the request and verify the destination, network and amount against the custody wallet. The assigned reviewer approves the request before signing and broadcasting it externally. The reviewer can return reserved funds before sending or record the broadcast transaction ID after sending. Record the on-chain transaction ID once per request. The API records the operator's attestation; the isolated signing worker only collects eligible deposits and does not sign player payouts or automatically confirm withdrawals.

## Player management and notifications

Under **Admin → Users**, search by full or partial email, username or account ID. Use the status filter to find active, suspended or banned accounts. Select a row for balances, deposit addresses, statistics, deposits, withdrawals, bet results, transactions and operator actions. Under **Controls**, enter a reason and review each adjustment, suspension, ban or restoration. Adjustments post a balanced journal. Bans and suspensions revoke player sessions immediately. A temporary suspension expires at the chosen time.

For a pending deposit, **Deposits → Hold credit for review** preserves the observation and blocks credit. Release the hold to let the watcher recheck the canonical block and confirmation count. Players receive a notification when the scanner detects a deposit and again when it credits the balance. EVM detection follows the configured reorganization safety lag. Outbound requests notify the player when requested, claimed for review, approved, returned or recorded as sent. The withdrawal receipt includes the operator's transaction hash.

Notifications persist in PostgreSQL. A long poll wakes after an event commits, including events written by another replica. Reopening the inbox loads saved activity and read state.

## Winter rewards and weekly prizes

The active reward program has **100 coin-wager player levels**. A new winter pack unlocks every ten levels (10 through 100). Each earned pack can be claimed once every rolling 24 hours, using the original catalog’s disclosed contents and odds. A claim posts its payout directly to the COINS ledger, stores the fair outcome, and sends a personal notification. The same approved request replays without awarding twice. Player profiles and the operator record show coin wager progress and ready packs.

The old 45-level Bronze-through-Amethyst VIP program and its claim UI are retired. Its endpoint returns HTTP 410 and migration 036 prevents new claims from an old replica. Historical bonus receipts, claims and frozen valuations remain available as audit evidence. Already earned catalog progress is preserved; settled Mines and Blackjack also count. Deposits, conversions, adjustments, free rewards and cancelled battles add no wager progress. Historical wagers use recorded valuations, never today’s market price; missing historical valuations are not invented.

The weekly coin leaderboard ranks **settled paid stakes** from Monday 00:00 UTC to the next Monday. Cancelled battles, free rewards and bots are excluded. Ties use player UUID order. The top 50 are displayed and an authenticated player’s position is calculated across everyone. The top-ten prize schedule is **150,000 / 100,000 / 70,000 / 50,000 / 40,000 / 30,000 / 20,000 / 15,000 / 15,000 / 10,000 coins**. Empty ranks are not paid. Each replica checks for due seasons every minute; leaderboard reads also catch up. A shared/exclusive transaction barrier closes week-boundary races, and payout records/journals commit once per season. After downtime, missed seasons settle in bounded batches.

Player and admin transaction histories filter deposits, withdrawals, conversions, bets, rewards and balance adjustments. Crypto deposit/withdrawal receipts keep their original asset, chain and transaction ID. The winter snow is decorative, optional, synchronized between tabs, disabled for reduced motion and paused in background tabs.

## Player security and interface

Players enroll an authenticator in **Account → Security** by verifying their current password, scanning the locally generated QR code or entering its manual Base32 key, and confirming a six-digit code. Pending enrollment expires after ten minutes. The authenticator secret uses the existing vault encryption; ten independent recovery codes are displayed once and stored only as user-bound hashes. Each TOTP time step and each recovery code can succeed once. Concurrent requests serialize consumption. Login, password changes, session revocation and authenticator removal enforce the enabled factor. Activation and removal revoke other sessions; changing or recovering a password revokes all old sessions. Players can review session timestamps and sign out other sessions from Security.

**Forgot password** accepts the account email, a new password and an enabled authenticator code or an unused recovery code. It does not send a reset email or create a new session. Recovery failures use a generic response; account counters survive failed transactions and supplement the shared IP limits. Save recovery codes separately from the authenticator app. Security changes appear in the player's notification history.

Migration 033 starts `player_2fa_available` at false. `deploy.sh` enables enrollment after both API replicas are updated and healthy. After any player enrolls, rollbacks must retain player-factor enforcement; do not serve a pre-033 API image against enrolled accounts. Database backups retain the encrypted authenticator records and require the original vault key.

The player interface shares one sound preference across games and account notifications. Previously unread history stays silent; new receipts can chime, and the main logo navigates silently. Wager actions disable when the exact entered minor-unit amount exceeds the current selected-currency balance, with an available-balance hint. Cash-out and stopping autobet remain available during active rounds. Server-side balance checks still decide every wager. Weekly standings show the top 50, this week's totals and the authenticated player's rank even outside the top 50; cancelled battle entries are excluded, and week boundaries use UTC.

## Collection reporting

**Admin → Sweeps** provides all job states, public deposit and transaction references, exact credited and collected amounts, sponsor and collection steps, broadcast counts, confirmation depth, and receipt timestamps. Filter by network, asset, status or public reference; cursor pages can be exported as CSV. Exported amounts remain exact integer minor units with a decimals column. Unqueued credited deposits show why collection is waiting, including paused sweeps and amounts below the collection minimum.

Fee-wallet cards show native ETH, BNB and POL reserves at a verified canonical block, the last successful check, the worker state, and existing sponsorship limits. SOL pays from the deposit and has no shared sponsor wallet. Balance refreshes share a one-minute claim across replicas and use the existing RPC request budget. Failed reads preserve the last verified value and timestamp; an unknown balance is not displayed as zero. These reads cannot sign a transfer or pause deposit issuance.

Migration 032 records actual network fees from newly verified final receipts. Reserved fees remain distinct ceilings. Historical receipts without an actual fee remain unknown; the dashboard never substitutes a ceiling as the paid fee. Existing sweep controls, destinations and sponsorship limits are retained. The deployment stops the signing worker while migrations acquire schema locks, then restarts it after updating the API replicas.
